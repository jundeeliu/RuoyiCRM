# RuoyiCRM `master_tenant` expand/contract and canary runbook

Scope: the repository's `sql/rycrm-master.sql` defines `master_tenant.host`, while the current `MasterTenantMapper.xml` selects and writes `host_name`, `status`, and `expiration_date`. The old `sql/update_20220311.sql` renames `host` in place; this plan keeps both names during coexistence. The SQL targets MySQL 8.4.11 as observed in the isolated CRIT-10 stack. It is a **candidate**, not a production-qualified migration.

## Authority and prerequisites

One master database is authoritative throughout the rollout. Legacy and Boot 4 application pods may both read it; the compatibility triggers mirror `host` and `host_name` writes and reject conflicting changes. No shadow or test writer may connect to a production database. Back up and restore a disposable clone first, record its schema and engine tuple, inspect existing triggers, and prove the exact online DDL and lock behavior with representative load. MySQL DDL is not transactionally rolled back; the `99_contract_manual.sql` file is intentionally outside the canary path.

Block the rollout if the existing table already has `host_name`, `status`, or `expiration_date` with unknown definitions, if `master_tenant` already has INSERT/UPDATE triggers, if any `tenant` key is null/duplicated, if source and target application behavior differs, or if a clone backup/restore and post-cutover write recovery are unproven. Do not run the supplied SQL against an unknown schema. The checked-in `00_preflight.sql` is read-only; compare its result with the source DDL and current Mapper before any write.

## Phase order

1. **Expand:** run `deploy/cutover/sql/00_preflight.sql`; verify the expected legacy schema and zero conflicting triggers. On a disposable clone, run `01_expand.sql`. Its `ALGORITHM=INSTANT, LOCK=DEFAULT` causes an unsupported instant operation to fail instead of silently rebuilding the table. MySQL permits only `LOCK=DEFAULT` with `ALGORITHM=INSTANT`; even instant DDL takes metadata locks briefly. Repeat the exact operation and lock observation in the approved deployment environment before any production change.
2. **Compatibility:** run `02_compatibility.sql` after expansion, before mixed-version traffic. The INSERT and UPDATE triggers copy the changed host field to its peer. If both fields change to different values, the statement fails. Verify old and new write paths and rollback to legacy against a disposable clone. This trigger pair is a compatibility mechanism, not a substitute for application contract tests.
3. **Backfill:** inspect `conflicting_rows` in `03_backfill.sql` and stop unless it is zero. Execute the bounded UPDATE repeatedly until `remaining_rows = 0`; record counts and row-level reconciliation without credentials. Avoid scheduling overlapping backfill workers. Backfill is one direction only; the triggers keep subsequent writes in sync.
4. **Canary:** deploy distinct legacy and Boot 4 workloads with Kubernetes pod label `version=legacy` or `version=boot4`, both selected by Service `ruoyicrm-web` in namespace `ruoyicrm`; verify readiness and destinations. Apply `istio/destination-rule.json` and first `istio/000-boot4.json`, then advance exact Boot 4 weights **1%, 10%, 50%, 100%** using the matching checked-in JSON manifests. JSON is valid Kubernetes YAML. For each stage, hold for a measured observation window, compare API/tenant behavior and database writes, and preserve the legacy pods and schema. The repository currently contains no corresponding Kubernetes workloads, Service, Istio installation, or Prometheus deployment; verify these identities in the real target before applying anything.
5. **Rollback:** the sentinel defaults to dry run. For each evaluation it obtains four Prometheus instant vectors, requires a single fresh finite aggregate, and chooses rollback on missing/insufficient telemetry, Boot 4 5xx ratio ≥5%, or Boot 4 p95 ≥2× legacy p95. `--apply` additionally requires an exact Kubernetes context and namespace UID. It reads the owned VirtualService, verifies its 1/10/50/100 stage and plan annotation, then uses `kubectl replace` with the observed `resourceVersion` to set legacy=100, Boot 4=0. A concurrent route mutation causes replace to fail rather than overwrite it. `--watch --interval-seconds 5` polls continuously and exits on the first rollback decision; deploy it under an approved supervisor with alerting. No seconds-level reaction time has been measured or promised. Example dry run: `python3 deploy/cutover/rollback_sentinel.py --prometheus-url https://PROMETHEUS_HOST`.
6. **Contract:** only after the observation period, release-owner signoff, drained legacy writers, verified recovery of writes made during the Boot 4 window, and a restore drill, run `90_contract_preflight.sql`. `divergent_host_rows` and `invalid_status_rows` must both be zero; the expected compatibility trigger count is two. `99_contract_manual.sql` removes triggers and `host` and prevents further legacy rollback. It is a separate manual change and must not be included in automated canary deployment.

## Telemetry and rollback control

`deploy/cutover/prometheus-queries.json` uses standard Istio `istio_requests_total` and request-duration histogram series filtered to `destination_service=ruoyicrm-web.ruoyicrm.svc.cluster.local`, `destination_workload_namespace=ruoyicrm`, and `destination_version` legacy/boot4. It assumes destination reporting and the version labels above. Check that each query returns exactly one current unlabelled sample before arming automatic rollback. A missing series is treated as unsafe and triggers rollback, but an invalid Kubernetes identity blocks mutation. The application POM has an Actuator starter but no evidenced Prometheus registry or live Istio topology, so live telemetry remains unverified.

For an **approved isolated test cluster**, invoke `python3 deploy/cutover/rollback_sentinel.py --prometheus-url https://PROMETHEUS_HOST --apply --context EXACT_CONTEXT --namespace-uid EXACT_UID`. Production application of any manifest, SQL, or rollback command requires the deployment owner's separate release workflow and evidence. Do not hardcode tokens in this repository. The script emits only decision/reason/applied JSON; archive query outputs, route resource version, timestamp, context identity, and post-rollback traffic checks in the release evidence store.

## Exit criteria and limitations

Local unit tests validate the route weights and rollback decision/identity guards. They do not prove Istio routing, Prometheus scrape labels, SQL online behavior under load, trigger semantics on MySQL, transaction preservation, a zero-downtime outcome, or rollback latency. The exact source/target physical stack evidence and independent verification must precede an E4/E5 or production-ready claim. Recovery must reconcile writes accepted during the Boot 4 window before reducing or removing Boot 4 pods.
